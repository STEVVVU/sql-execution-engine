# Initial SQL baseline

[Hosted run 39729583363](https://github.com/STEVVVU/sql-execution-engine/actions/runs/39729583363) measured source `58adbf2f82acc2df2375615d6b941d5d06a11364`. Its `sql-benchmark-39729583363` artifact contains every CSV result, physical plan, raw timing and resource record. The result manifest SHA-256 is `7a659ba53a28b8aec89b7940096120ca22cd7842a54a06f62bc0a084bb32d9ac`.

The runner used Ubuntu, Linux 6.17.0-1022-azure, glibc 2.39, an AMD EPYC 7763 with two assigned physical cores and four logical CPUs, and Rust 1.99.1 release optimization. Each query has one warmup and five measured repetitions per side, reversing side order between repetitions. All 270 invocations exited zero. All 15 size/query combinations matched the exact CSV digest across all sides and repetitions. Temporary fixtures were removed after retained evidence was written.

The deterministic disk CSV has `id=i`, `category=i%100` and `value=(i*7919)%1000`. The dimension has 100 unique category keys. Batch size is 8192. The custom executor uses one or four workers; DataFusion uses its default planner and four target partitions through `--reference-tuned`. Every fresh CLI invocation includes startup, file decoding, planning, execution and consumed CSV output. The OS cache is warm after warmup; no host cache eviction or spill is involved.

For the million-row dimension join, maximum measured peak process RSS was 372.64 MiB, 371.86 MiB and 59.17 MiB respectively. GNU time reports process resources; the raw artifact retains every sample. No percentile above the five-run median is inferred from this small repetition count.

The four-worker custom join showed a substantial wall-time and memory gap. [Separate Callgrind run 39732211058](https://github.com/STEVVVU/sql-execution-engine/actions/runs/39732211058), source `1f73fcafb08c869f03c1b94cb922222c3c352543`, used the exact 100k-row join fixture and verified both original data and result hashes. Artifact `sql-callgrind-39732211058` retains raw profiles and source annotations. The optimized build with line information executed 441,877,395 instructions for custom one worker, 445,494,568 for custom four workers and 181,752,835 for DataFusion. All three exited zero and returned the same expected digest.

In the four-worker source profile, the serial partition function ran 200,100 times and accounted for 66,833,400 inclusive instructions (15.0% of the whole process). ScalarValue extraction accounted for another 26,813,400 instructions (6.02%); the join and grouping paths convert each input key and repeatedly hash scalar vectors. This supports reducing key/hash overhead. Instruction counts do not measure cache contention or establish the cause of the four-worker wall-time regression. A candidate that reuses the existing ahash dependency is unmeasured; no optimization benefit is claimed yet. These measurements establish no general engine speedup, SQL completeness or disk-spill capability.

Reproduce the measured path with `cargo build --release --locked --jobs 2` and `python3 scripts/benchmark.py --output evidence/benchmark`. Run `.github/workflows/profile.yml` for separate instruction profiles; instrumented profile wall times are excluded from benchmark comparisons. Future matched CLI comparisons can use hyperfine while retaining these fixture and exact-result checks.
